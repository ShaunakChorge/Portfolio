    AI audit finding generator and drafting engine

    Audit findings drafted by Artificial Intelligence (AI), and not allowed to make things up.

    The AI audit finding generator is a standalone service at Claptek that turns short audit checklist notes into draft findings, three versions each. Code-level checks block any invented figure, date or owner, so the AI cannot add facts that were not in the auditor's note.

    Overview

    Why this matters

    Audit teams record what they find in short checklist notes. Each note must become a formal finding with a title, a description, a recommendation and a severity rating. That write-up is slow, and a vague or wrong one leaves the people responsible unsure what to do. Faster, steadier drafting can give auditors time back for testing controls.

    A good result is an auditor who types a short note and receives three draft findings in seconds, worded like earlier findings from the same bank. No draft adds a figure, date or owner that the auditor did not write. A person reviews every draft, and a whole checklist can be drafted in one pass.

    The story

    The problem: slow, uneven audit write-ups

    The problem

    Auditors spend hours turning terse checklist notes into well-formed findings. Simple AI drafting tends to invent figures and names. Both cost the business, because slow write-ups take time from real audit work. An invented figure, date or owner is worse, because someone may act on it or trust the report less.

    What I built

    I built the drafting engine as a standalone FastAPI service (a Python web framework). An auditor's checklist note arrives with its verdict, and simple checks run before any AI time is spent. The service then finds similar past findings to use as writing examples. An AI language model that runs on Claptek's own servers writes the title, description, recommendation and severity, in three versions: short, balanced and detailed. Hard checks in code follow: any draft containing a figure, date or owner that is not in the auditor's note is rejected. Bulk mode drafts a whole workbook into a reviewable grid, and the client's audit product shows the three versions on its own edit screen.

    What made it hard

    1. 01

      Models invent details

      Asked to write a finding, a language model fills gaps with plausible figures, dates and names. In an audit, one invented fact can mislead the people who must act on it.

    2. 02

      Thin, uneven notes

      Checklist notes are short, and each bank words things its own way. The service had to write a complete finding from very little, in the style of that bank's earlier findings.

    3. 03

      A very slow response

      At one point a single request took 7.9 minutes, which no auditor will wait for. The cause was buried in the way the system called the AI models, so I had to find it by testing.

    4. 04

      Fitting a live product

      The drafting had to work inside an audit product that another team owns, built with Spring Boot and React. The feature also had to be easy for that team to adopt.

    How it is built

    How the audit drafting service works

    1. 01Auditor's notechecklist verdict and observation
    2. 02Simple checksrun before any AI time is spent
    3. 03Past findingssimilar examples found by keyword search
    4. 04AI draftmodel on Claptek's own servers
    5. 05Code checksinvented figures, dates, owners rejected
    6. 06Three versionsshort, balanced, detailed, for review
    1. 01

      One settings file per bank holds that bank's categories, example findings, pass and fail wording and required fields, so one codebase serves several banks.

    2. 02

      Simple checks on the auditor's note run first, before any AI time is spent. A search step then finds similar past findings by keyword matching (TF-IDF, a keyword-weighting method) and passes them to the model as writing examples.

    3. 03

      An AI language model on Claptek's own servers writes the title, description, recommendation and severity, using the auditor's note and the retrieved examples.

    4. 04

      Code-level checks run on every reply. A draft is rejected if it holds a figure, date or owner that is not in the auditor's note. With no usable note, the service returns an outline with no specific facts for the auditor to complete.

    5. 05

      Three versions of every finding: short, balanced and detailed, so the auditor can pick one and edit it.

    6. 06

      Bulk mode: the user uploads a checklist workbook and maps its columns in the browser. Each row is drafted into a reviewable grid where it can be accepted, edited or rejected, then exported. A written summary report groups the findings by theme.

    7. 07

      The client's audit product, built with Spring Boot (a Java framework) and React (a web screen library), gains a drafting action on its edit screen. Its backend gathers the item's details with one database query and sends them to this service, and the screen shows the three versions inline.

    Decisions

    Design decisions and trade-offs

    • Check in code, not in the prompt

      ChoiceI enforce the rule that every figure, date and owner must appear in the auditor's note with a check in code, not only with an instruction in the prompt.

      WhyAn instruction is a request that a model can ignore. A check in code rejects the draft every time, so the guarantee does not depend on how the model behaves that day.

    • Measure the slowdown before fixing it

      ChoiceWhen requests took 7.9 minutes, I tested the AI model server directly instead of relying on its documentation, found the hidden extra processing, and compared four candidate models.

      WhyGuessing at fixes wastes time. Direct tests showed what the server really did. Once the hidden processing was off, time per request fell to 16.9 seconds and accuracy stayed unchanged.

    • Let the AI label, let code count

      ChoiceIn the summary report, the AI only labels each finding with a theme and an owner. Code does all the counting, and an owner label is accepted only if it appears in that row's own recommendation.

      WhyCharts built from AI-written numbers can look right and be wrong. Here code does the counting from the spreadsheet itself, and the AI only supplies the labels.

    • Reuse the product's own sign-in

      ChoiceI made the drafting action use the audit product's existing sign-in, so it adds no new login to manage.

      WhyDrafts are built from confidential audit data. Reusing the product's existing access control keeps a single set of access rules to maintain.

    Results

    Results: no invented facts, much faster

    Every number comes with how it was measured. The limits are part of the result.

    Results

    • 0 invented facts across 27 checked draft versions, measured on real audit notes: none contained a figure, date or owner that was missing from the auditor's note.
    • Time per request fell from 7.9 minutes to 16.9 seconds, about 28 times faster. The cause was hidden extra processing in the way the system called the AI models. I fixed it and compared four candidate models, and accuracy stayed unchanged.
    • 313 automated tests pass, and the code passes style and type checks.
    • The client's audit product team adopted the feature the day after handover. I had handed it over with a self-contained integration guide.
    • A reviewer gets three versions of each finding and can accept, edit or reject every row of a bulk run.

    Limits to keep in mind

    • A person must still review every finding. The checks stop invented figures, dates and owners, but they cannot judge whether the wording or the severity rating is right.
    • The result of zero invented facts comes from 27 draft versions, which is a small sample, and the 16.9 seconds was measured on Claptek's own servers. I would measure both again on your notes and your hardware.
    • Finding similar past findings uses keyword matching, so it can miss an example that says the same thing in different words.
    • Today the service does not record who accepted or edited a draft, and it has no user roles of its own.

    FAQ

    Questions about the audit drafting engine

    Can AI write audit findings without making things up?

    Yes, when code checks every draft. Every figure, date or owner in a draft must appear word for word in the auditor's own note. A check rejects any draft that adds one. Across 27 checked draft versions it produced no invented facts, though a person still reviews each finding.

    Could the same approach work on my reports or tickets?

    The method is not specific to audit. It finds relevant evidence, uses an AI model hosted on your own machines and checks the output in code. I would first test it on a sample of your own documents to see how well it holds.

    Why did drafting get faster, from 7.9 minutes to 16.9 seconds?

    The cause was hidden extra processing: the AI model was doing long, hidden reasoning before each answer. I found it by testing the model server directly, fixed it and compared four candidate models on speed and draft quality. Time per request fell from 7.9 minutes to 16.9 seconds, about 28 times faster, with accuracy unchanged.

    What happens when the auditor's note is too short?

    The service does not guess. When there is no usable note, it returns an outline with no specific figures, dates or owners, and the auditor completes it. This stops a plausible but made-up story from being presented as fact, and it matches the rule enforced by the code checks.

    Can it draft a whole audit checklist spreadsheet at once?

    Yes. In bulk mode the user uploads a checklist workbook and maps its columns. Every row is drafted into a grid that looks like a spreadsheet, with all three versions of each finding. Reviewers accept, edit or reject each row, export the result and get a written summary report.

    How does it fit into an existing audit product?

    The drafting engine is its own FastAPI service. A drafting action on the audit product's edit screen has the product's backend gather the item's details and send them across, and the three versions appear on the same screen. I handed it over with a self-contained integration guide, and the client's team adopted it the day after handover.

    Can it follow our own audit categories and wording?

    Yes. Each bank has its own settings file holding its categories, example findings, pass and fail wording and required fields, so one codebase serves several banks. The search step also shows the model similar past findings, which helps drafts follow earlier house style. I would build the settings from your own past findings.
