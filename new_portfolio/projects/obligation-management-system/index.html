    Overview

    Why this matters

    Banks, lenders and other regulated companies receive circulars, permits and regulations that set out what they must do. Someone has to read each long document, list the duties, say who owns each one and note which clause it comes from. A missed duty can mean a penalty or an audit finding, so the work is slow and careful.

    A good result is an evidence-linked obligation list that a compliance officer can check quickly. Each line says who must do what and under which section, and the exact source sentence is highlighted in the original PDF beside it. The reviewer confirms or corrects the list instead of searching through pages to find where each duty came from.

    The story

    The problem: obligations hidden in long documents

    The problem

    Compliance teams build obligation lists by hand from long regulatory PDFs, and the page numbers an AI model gives for them cannot be trusted. Hand work is slow and must be repeated whenever a rule changes. Wrong page references send reviewers to the wrong place, so they may stop trusting the list and check everything again, which removes the time saved.

    What I built

    I built the extraction in four steps. First, the document is split at page boundaries, and a merge step rejoins obligations that cross a break. Second, for each piece an AI language model on Claptek's own servers lists the obligations in a fixed format: an owner (who must act), a category from a fixed list, a risk or control tag and the section, plus the source sentence copied word for word. Third, code searches the PDF for that sentence and reads the page and highlight position from the document itself, instead of trusting a page number from the model. Fourth, a side-by-side preview shows each obligation beside its highlighted evidence.

    What made it hard

    1. 01

      Unreliable page numbers

      An AI model can state a page number for each obligation, but those numbers were wrong 56% of the time. A reviewer sent to the wrong page loses trust in the whole list.

    2. 02

      Long documents

      Regulations run to many pages and a model reads only a piece at a time. Duties that cross a page break could be split or lost unless they are joined again.

    3. 03

      Many kinds of document

      Permits, circulars, master directions and know-your-customer rules are written differently. The method had to work on all of them without special code for each type.

    4. 04

      Measuring fairly

      A system built around a few sample documents can look better than it is. I needed a fair test, so I kept some documents apart from those I used while building and compared the same code with one setting changed.

    How it is built

    From regulation to checked obligation list

    1. 01Regulatory PDFcircular, permit or regulation
    2. 02Split by pagepieces cut at page boundaries
    3. 03AI extractionobligations with word-for-word quotes
    4. 04Quote matchingcode finds each quote in the PDF
    5. 05Linked listobligations beside highlighted evidence
    1. 01

      The document is split at page boundaries, and a merge step joins obligations that cross a page break, so a duty is not cut in half.

    2. 02

      For each piece, an AI language model hosted on Claptek's own servers extracts the obligations. It records each in a fixed format: an owner, a category from a fixed list, a risk or control tag and the section, so output stays consistent from one document to the next.

    3. 03

      A locator finds each word-for-word quote in the PDF, using PyMuPDF (a PDF reading library), and reads the page number and highlight position from the document itself. I tested it on a set of reference records before connecting it to the live pipeline.

    4. 04

      A side-by-side PDF preview (pdf.js, a browser PDF viewer) highlights the evidence for each obligation. For scanned pages that pdf.js cannot draw, the preview falls back to an image of the page at matching scale, so highlights stay in place.

    5. 05

      Generation can be cancelled, which frees the model's memory and keeps the extracts already finished, so a long run resumes instead of restarting.

    6. 06

      A second-read step, so far only tested in a controlled comparison and not yet in the live service, quotes the sentences that impose duties, drops every quote that is not found word for word in the PDF, and writes records from what is left.

    7. 07

      A FastAPI backend (a Python web framework) serves the extraction, a React screen shows the list and the preview, and Docker packages the whole service for easy installation on a server.

    Decisions

    Design decisions and trade-offs

    • Find the quote instead of trusting the page

      ChoiceI ask the model to copy the source sentence word for word, then let code find that sentence in the PDF and read off the page and highlight position.

      WhyThe model quoted text well but stated page numbers badly: its page numbers were wrong 56% of the time. Matching text is exact work for code, so each job goes to the tool that does it best.

    • Measure each speed-up before keeping it

      ChoiceI profiled where processing time went, tested each proposed speed-up and kept only those that helped. Running two copies of the model side by side gave no net gain, so I did not use it.

      WhyMeasurement showed the limit was how fast the machine can read the model's memory, which a second copy cannot widen. The changes that did help cut a six-document run from 80.4 to 60.0 minutes.

    • Check every quote against the source

      ChoiceIn the second-read step I tested, a first pass only quotes sentences that impose duties. Each quote is checked word for word against the PDF and dropped if it does not match.

      WhyA model can produce a plausible sentence that is not in the document. Dropping every unmatched quote lets the extra pass add coverage without adding invented quotes.

    • Test fairly before claiming a gain

      ChoiceI compared the same code with one setting changed, on documents kept apart from those I used while building the step, and repeated identical runs to see how much results vary by chance.

      WhyOne run on the documents used while building can flatter a result. Measuring the run-to-run spread shows which gains are real and which are noise.

    What I tried first, and what changed

    First attempt. The AI model stated the page number for each obligation. Checked against the source, those page numbers had been wrong 56% of the time, so a reviewer following them would often land on the wrong page.

    What changed. I asked for a word-for-word quote instead, and wrote code that finds the quote in the PDF and reads off the page and highlight position. Now 97.2% of 1,266 production records link to an exact, highlightable passage.

    Results

    Results: obligations linked to their source

    Every number comes with how it was measured. The limits are part of the result.

    Results

    • 97.2% of 1,266 production records link to an exact, highlightable passage in the source PDF. Before this, the page numbers the AI model stated had been wrong 56% of the time.
    • 100% of records carry a word-for-word source quote, so a reviewer can check each record against the passage the model quoted.
    • In a controlled test of an extra reading step (not yet live), recall (the share of obligations found) rose from 32% to 69% for Basel III rules and from 69% to 82% for KYC (know-your-customer) rules, on documents kept apart from those used while building.
    • Processing time for a six-document benchmark fell from 80.4 to 60.0 minutes, after I measured where the time went and kept only the changes that helped.
    • The same process reads permits, circulars and regulations with no domain-specific code.

    Limits to keep in mind

    • About 2.8% of production records were not matched to an exact passage, and a person should still review the whole list. Those records still carry the quote the model gave, so a reviewer can search for it by hand.
    • The recall gains come from a controlled test of an extra reading step that is not yet in the live service. I report Basel III banking rules and KYC rules only, and have not measured data protection, safety or tax rules.
    • A reviewer may still find a duplicate record or a duty assigned to the wrong party, so a person should check the whole list.
    • I have not built support for documents in other languages, or for translation. Lists are also not versioned, so a revised circular needs a fresh run and a manual comparison.

    FAQ

    Questions about obligation extraction

    How do you extract obligations from regulatory documents?

    Split the document into pieces, then ask an AI language model to list each obligation and quote the source word for word. Code then finds that quote in the PDF to work out the page and highlight position, instead of trusting the page numbers the model gives. A person should still review the list.

    How do you keep the citations accurate?

    The AI returns a word-for-word quote, and code then finds that quote in the PDF to work out the page and highlight position. In the production data I measured, 97.2% of 1,266 records were located exactly. This replaced page numbers the model had often got wrong.

    Does it only work for one kind of regulation?

    No. It is not tied to one domain. The same process has read environmental permits, banking master directions, Basel III circulars and KYC rules without any domain-specific code. A new client could bring their own documents, though I would first check results on a sample.

    What counts as an obligation in a regulatory document?

    An obligation is a duty the document places on someone: who must do what, and under which section. Examples are a duty to report, to keep records or to stay within a limit. The service lists each one with its owner, a category and a risk or control tag.

    What does the 97.2% figure actually measure?

    It measures how many of 1,266 production records could be linked to an exact passage in the source PDF, found by matching the model's word-for-word quote. Every record has a quote. The remaining 2.8% were not matched to an exact passage, so a reviewer should check those by hand.

    Does it replace the compliance reviewer?

    No. It gives a reviewer a head start: a structured list in which each duty sits beside its highlighted source sentence, so checking should be faster. A person should still review the list and correct mistakes, such as a duty placed on the wrong party. The aim is faster, better-evidenced review, not unchecked automation.

    Where does the AI model run when it reads my documents?

    In this project the AI language model runs on Claptek's own servers, not on an online AI service. For a new client, I would check what hardware you have, because larger models need stronger machines, and then run the model where your documents are allowed to stay.
