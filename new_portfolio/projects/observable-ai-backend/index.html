    FastAPI OpenTelemetry tracing for an AI backend

    An AI server you can debug from the outside, with LLM observability built in.

    This FastAPI OpenTelemetry tracing project is an AI server with LLM (large language model) observability built in. A request ID follows every call through logs, metrics and traces (viewed in Jaeger). This means a slow or failing call can be explained from the outside.

    Overview

    Why this matters

    A business that puts an AI model behind a support tool, a report or a customer chat needs to know when that feature is slow, failing or quietly using a backup. If the team cannot see inside a request, every complaint turns into guessing: was it the model, the data or its own code? Visibility turns that guessing into a short search.

    A good result lets anyone on the team take one complaint, find that exact request, see which step took the time and read the log lines for it. It also shows how heavily the AI servers are used, whether each service is running, and alerts people when something needs attention. This case study covers the request level and the server level, and says which part is which.

    The story

    The problem: AI servers that are hard to debug

    The problem

    An AI server can return a success code and still be slow, degraded or quietly answering from a different model. Nobody finds out until users complain. By then the cost is already paid: lost trust, a busy support queue and engineers searching logs with no way to tie a complaint to one request. Without counters, nobody can say how often it happens.

    What I built

    I built a small AI server in FastAPI. For each question, an AI model picks one of three business actions, the action runs, and the model writes a short answer. Every log line and trace step of a request carries the same request ID, and the caller gets it back in the response. A few hand-written metrics count requests, AI response time, tokens (the small pieces of text an AI is billed by) and model fallbacks. Three Groq models are chained, each with its own time limit, and the response carries a "degraded" flag, so a silent fallback becomes visible. At work, I added resource use, service status and alerts to the LLM observability of the company's AI servers.

    What made it hard

    1. 01

      Failures that look like success

      A missing or slow model can still end in a success code, because a backup path answers. That happened to me during testing, and my first logs and metrics gave no clear sign of it.

    2. 02

      Finding the slow step

      One request passes through a model call, a business action and a second model call. Total time alone does not say which step is slow. Only a step-by-step view does.

    3. 03

      Telemetry that stays safe and small

      Logs can leak customer text and grow fast. Metrics can multiply into thousands of series if a label holds free text. I kept questions and answers out of logs and used a short, fixed set of labels.

    4. 04

      Seeing the servers, not only requests

      A trace explains one call. It does not show whether the machine behind it is short of capacity or a service has stopped. That needs resource use, service status and alerts as well.

    How it is built

    Request IDs, metrics and traces

    1. 01Questionrequest ID created
    2. 02AI routesmodel picks one action
    3. 03Action runsruns on made-up data
    4. 04AI answersshort answer, flagged if no AI answered
    5. 05Signalslogs, metrics and traces recorded
    6. 06Server watchseparate company work: usage, status, alerts
    1. 01

      An AI server with an /ask endpoint (a web address the app answers on). An AI model picks one of three business actions: looking up tickets, creating a ticket or running a sales report. The action runs on made-up data, and the model then summarises the result.

    2. 02

      A chain of three Groq models, each with a 10-second limit and the library's own retries switched off. If all fail, or no API key is set, a simple keyword router answers and the response is marked "degraded". The service therefore runs with no API key or internet.

    3. 03

      One request ID, which is also the trace ID, appears on every JSON log line written during a request, on every trace step and in every /ask response, including errors. The question and the model's answer are deliberately kept out of the logs; only short error details are logged.

    4. 04

      Hand-written Prometheus metrics: requests by status code, request time, errors by type, AI call time, tokens, model fallbacks and requests in progress. Labels are never free text, so the stored data stays small.

    5. 05

      OpenTelemetry traces are pushed to Jaeger. The web request and the outgoing AI call are traced automatically, and I added spans for routing, the action, the summary and each model call. Health and metrics calls are left out.

    6. 06

      A Docker Compose setup starts the app, Jaeger and Prometheus together. Configuration is baked into the images and every host port is a setting, so the stack can be copied to another machine and started the same way.

    7. 07

      At the company, resource use, service status and alerts were added to the LLM observability of its AI servers. This part is confidential and is not part of the personal repository.

    Decisions

    Design decisions and trade-offs

    • Tracing as the one big improvement

      ChoiceOf seven options in the brief, I chose OpenTelemetry tracing, and I used the trace ID as the request ID on its log lines and responses.

      WhyMetrics show that a request was slow and logs show what the code did, but only a trace shows where the time went. One shared ID then links all three.

    • Hand-written logs and metrics

      ChoiceI wrote a short log formatter and picked the metrics myself, instead of using ready-made helper libraries that choose them for you.

      WhyWhat to measure should be my decision and easy to explain. A helper library would have hidden the key idea, which is how the trace ID reaches each log line.

    • Fail fast, then try another model

      ChoiceEach model gets a 10-second limit and the provider's own retries are off, so a failing model hands the request to the next one in the chain.

      WhyThe provider's defaults could hold one hung model for up to 180 seconds. With my limit the worst case for one AI call is about 30 seconds across three models.

    • Leave out the large monitoring stack

      ChoiceI declined Grafana, Loki, Tempo and Kubernetes, and used Jaeger and Prometheus on their own screens.

      WhyThe task needed metrics, logs and traces that could be used, not a dashboard product. The extra tools would have added setup time and more containers without adding anything the task needed.

    What I tried first, and what changed

    First attempt. I first set a single model, picked from the provider's public model list. On my key that model was not available, yet every request still returned a success code, because the keyword fallback quietly answered. The only sign was a flag in the response, and the log gave just an error class name.

    What changed. I replaced it with a chain of three models, ordered by the routing speed I measured (121, 492 and 545 milliseconds). I added the provider's error message to the log line and a fallback counter, so a failing first model shows up in monitoring even when users notice nothing.

    Results

    A slow step found in a trace

    Every number comes with how it was measured. The limits are part of the result.

    Results

    • A deliberately slow lookup (a join over 60,000 made-up tickets) was the largest step in a trace. Once indexed, that step fell from about 15 seconds to under 50 milliseconds, and the whole request from about 16 seconds to under 1 second (captured traces).
    • 10 automated tests that need no key or internet. They cover the health check, bad input, the unknown-region error, the metrics page, the AI path with a stand-in client, the model chain, the time limit and a provider failure.
    • A failing first model no longer hides. The fallback counter and the log line record it, and the trace shows a second attempt. When every model fails, the response is flagged "degraded".
    • A request that took about 12 seconds in testing was explained afterwards from the logs alone: the summary model hung, the 10-second limit fired and the second model answered in under half a second.
    • At the company, resource use, service status and alerts were added to the LLM observability of the AI servers. The details are confidential and are not published here.

    Limits to keep in mind

    • This is a job-application task, not a production system. The data is made up and held in memory, the slow lookup was planted on purpose, and the timings come from a single test setup, not real traffic.
    • Timings move with machine load: three repeat runs of the slow path took between 17.5 and 27.1 seconds. I report the captured pair as an example, not as an average.
    • The personal build records every trace, defines no alert rules and has no sign-in. A real service would sample traces, add alerts and secure access. The time limit covers AI calls only, not a slow business action.
    • The company work is confidential, so this page shows none of its code, screens or figures. What I can say is limited to what I added: resource use, service status and alerts.

    FAQ

    Questions about this backend

    What is observability in a FastAPI app?

    Observability means you can tell what a running app is doing from the outside, using logs, metrics and traces. For an AI server this is called LLM observability. A request ID is stamped on every log line and trace step. Prometheus metrics count requests, AI response time and tokens. OpenTelemetry traces in Jaeger show where each request spent its time.

    Is this a production system?

    No. The traceable AI server is a job-application task, not a production system. The slow lookup was planted on purpose and the timings come from made-up data. The monitoring I added at work was for real company servers, but it is confidential and not shown here. A real system for you would need your own traffic, security and hosting decisions.

    Can it run without an AI key?

    Yes. With no key set, the server falls back to a simple keyword router and templated answers, and marks every response as degraded. Five of the 10 tests run in that mode. The others use a stand-in for the AI client or check its settings, so none needs a key, an account or internet.

    Which part is a personal build and which is company work?

    The traceable AI server is my own job-application build, written alone and kept in a private repository. The company work is separate: I added resource use, service status and alerts to the LLM observability of the company's AI servers. That work is confidential, so I describe it here but show none of its code, screens or figures.

    What happens if an AI model fails or hangs?

    A model that is unavailable, rate limited or silent for 10 seconds passes the request to the next of three Groq models. The fallback counter and the log line record each failure, and the response stays normal. If all three fail, simple keyword logic answers and the response is marked "degraded", so the caller knows no AI model wrote it.

    Do the logs store customer questions or answers?

    No. The question and the model's answer are deliberately kept out of the logs; only short error details are logged. Each line holds the request ID, the chosen action, row counts and durations. That protects privacy and keeps log volume down. Timing detail for one request lives in its trace.

    What does AI server monitoring add to request tracing?

    Tracing explains one request: which step ran and how long it took. Server monitoring watches what sits behind all requests. Resource use shows how much capacity the AI servers are using, service status shows whether each one is running, and alerts tell people when something needs attention. At work I added these to the company's LLM observability.
