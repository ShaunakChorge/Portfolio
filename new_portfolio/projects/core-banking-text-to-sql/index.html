    Overview

    Why this matters

    Banks and other large organisations keep their records in databases that can hold more than a thousand tables. In some of them only a few specialists can write SQL, the language used to read those tables, so each new report waits in a queue. A tool that turns a plain question into a correct query removes that wait, but only if people can trust what it returns.

    A good result is an on-premise text-to-SQL assistant: it runs on the bank's own servers, so the bank's data stays inside the bank. It finds the right tables, writes a query that runs and returns the right accounts. Its quality is measured by running its queries on a real database, so a manager can see how often it is right before relying on it.

    The story

    The problem: answers locked in a huge database

    The problem

    The project's simple scoring rated the query writer at about 93% good. Actually running its queries showed that the share returning exactly the right rows was close to zero. Those scores checked whether the right tables were found and whether expected code values appeared in the query text, not whether the query returned the right rows. A team that trusts such a number ships wrong or empty reports and fixes the wrong things.

    What I built

    I built the measurement first: a test that runs each generated query on a real database and compares the returned rows with a known-correct query. It scores strict row matches and also the recall and precision of the accounts returned. Then I added a retry loop, limited to two passes. When a query fails or returns no rows, the model is shown the real error and real values from the database, and asked to fix it. A glossary of real code values in the prompt makes filters use values that exist. The client ruled out a larger model and any retraining, so the gains had to come from the pipeline itself.

    What made it hard

    1. 01

      A very large database

      A layout of 1,628 tables is too large to show a model in full for every question, so the few tables a question needs must be found first.

    2. 02

      Scores that flatter

      A query can look right and still return the wrong rows, or none. Only running it and comparing its rows with those of a query known to be correct shows the truth.

    3. 03

      Invented code values

      Many columns hold fixed codes, not words. A model that guesses a code writes a filter that looks right but matches nothing.

    4. 04

      Strict client limits

      The model had to run on the bank's own servers. A larger model and retraining were not allowed, so any gain had to come from how the system uses the model it had.

    How it is built

    How a question becomes a checked SQL query

    1. 01Plain questionAsked in everyday words
    2. 02Table searchShortlists tables from 1,628
    3. 03Query writerModel on the bank's servers
    4. 04Safety guardChecked before it runs
    5. 05Run and retryReal errors fed back, two passes
    6. 06Accuracy testRun offline on test questions
    1. 01

      Table search, built by my teammate: it finds the right tables for each question in a core-banking database of 1,628 tables, using methods that include keyword search (BM25).

    2. 02

      A language model (LLM) hosted on the bank's own servers with vLLM, a model-serving program, writes the Oracle query from the question and the chosen tables.

    3. 03

      The query safety guard, built by my teammate with a SQL parser (sqlglot), checks each generated query before it runs. The test data was also my teammate's work.

    4. 04

      The accuracy test, built by me, executes every generated query against a live database and compares its rows with those of a known-correct query. It reports strict row matches, accounts found (recall) and the correct share of results (precision).

    5. 05

      The self-correction loop, built by me and limited to two passes: when a query errors or returns no rows, the model sees the real error and real column values, then revises the query.

    6. 06

      A glossary of real code values from the database is added to the prompt, so filters use values that actually exist.

    7. 07

      Hosted entirely on the bank's own servers, model included, so no outside AI service is involved. Generation is fixed at zero randomness to keep test runs repeatable.

    Decisions

    Design decisions and trade-offs

    • Score by running the queries

      ChoiceI chose to judge quality by running each generated query on a real database, over scoring table matches and code strings in the query text.

      WhyStand-in scores read about 93% while the share of queries returning exactly the right rows was close to zero. Only the rows a query returns show whether it does its job.

    • Fix the loop, not the model

      ChoiceI chose a self-correction loop, limited to two passes, over asking for a larger model or retraining, which the client had ruled out.

      WhyThe database itself tells the model what went wrong: a real error, or no rows. The loop is capped at two passes, so a hopeless query cannot retry forever.

    • Show the model real code values

      ChoiceI chose to add a glossary of real code values to the prompt, over letting the model guess which codes a column holds.

      WhyGuessed codes look plausible but match nothing. With real values in front of it, the model writes filters that can find accounts.

    • Fix randomness for repeatable scores

      ChoiceI chose to set the model's generation to zero randomness, over leaving it free, so test runs stay repeatable.

      WhyWith random variation, a gain of a few points cannot be told from noise. Repeatable runs let each change be judged on its own.

    Results

    Results from running the queries

    Every number comes with how it was measured. The limits are part of the result.

    Results

    • After the self-correction loop was added, accounts found (recall) rose from 34% to 54% and the correct share of results (precision) from 19% to 27%, with no model change and no retraining. Both come from running the queries on a real database.
    • 100% of 40 held-out test queries (kept apart from the ones used while building) were valid against the live database layout.
    • Stand-in scoring had put quality at about 93%. Running the queries put the exact-match rate close to zero, so every later gain is measured against a realistic baseline.
    • Generation is fixed at zero randomness to keep test runs repeatable, so a change in score points to a change in the system rather than to chance.
    • The whole pipeline, including the model, runs on the bank's own servers, so no data, prompt or usage record leaves the machine.

    Limits to keep in mind

    • At 54% accounts found and 27% correct share of results, the output is a draft to review, not a finished report. A person should check a generated query before relying on its numbers.
    • Valid means a query fits the live database layout (100% of 40 held-out queries). It does not prove the rows are right. Recall and precision are the measures of that.
    • The figures come from one database with a core-banking layout, loaded with test data, and a prepared set of test questions. Another database or kind of question would need its own accuracy test before the numbers are trusted.
    • The gains came from how the system uses the model, inside the client's limits of no larger model and no retraining. I cannot say how far a bigger or tuned model would go.

    In a business

    Where this kind of solution fits

    Situations where a team could use the same approach. These are examples, not past clients.

    • Bank reporting teams

      Analysts wait for a data team to write each query. Text-to-SQL for banking may shorten that wait, if the queries are checked and the assistant runs on the bank's own servers.

    • Audit and compliance teams

      Reviewers want quick answers, such as which accounts meet a condition, drawn from live data, with the query shown so the answer can be checked and repeated.

    • Companies with a very large old database

      Hundreds or thousands of tables and few people who know them. Table search plus query writing can help, and an accuracy test shows whether it is good enough to use.

    • Teams with a text-to-SQL prototype

      A demo looks good on simple scores, but nobody has run the queries. An accuracy test on real rows shows the true quality, and a correction loop may lift it without a new model.

    FAQ

    Questions about text to SQL

    What is text to SQL?

    Text to SQL means asking a database a question in everyday words and having an AI language model write the SQL query that answers it. The query is then run against the database. The hard parts are choosing the right tables and checking that the query is correct, which is why this project measures results by running queries.

    Is text to SQL safe for a bank database?

    It can be, with controls. Here the AI model runs on the bank's own servers, so no data, prompt or usage record leaves the machine. A query safety guard also checks queries before they run. My teammate built that guard; I built the accuracy test that compares returned rows with a correct query.

    How do you measure whether the generated query is right?

    By running it. The accuracy test executes the generated query on a real database and compares the rows with a known-correct query. Recall is the share of the right accounts the query returns; precision is the share of returned accounts that are right. These replaced simple scores that had overstated quality.

    Does any data leave the machine?

    No. The assistant runs fully on the bank's own servers, so no data, prompt or usage record leaves the machine. The AI model is hosted there too, so no online AI service is involved. For another project, the first step is to check that the servers are strong enough to run the model.

    Why did the first accuracy score say 93% when real accuracy was far lower?

    The first scores checked stand-ins: whether the right tables were found and whether the expected code values appeared in the query text. A query can pass both checks and still return wrong or empty results. Running the queries on a real database showed that exact row matches were close to zero, so I replaced the stand-ins.

    Which parts of the text-to-SQL assistant did you build yourself?

    I built the accuracy test and the self-correction loop, plus the code-value glossary in the prompt. A Claptek teammate built the table search, the query safety guard and the test data. It was a focused part of a two-person effort.

    Did you retrain or replace the AI model to raise accuracy?

    No. The client allowed no larger model and no retraining, so the model stayed as it was. The gain came from the self-correction loop: when a query failed or returned nothing, the model saw the real error and real column values and tried again, up to two passes. Recall rose from 34% to 54%.
