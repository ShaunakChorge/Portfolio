    Overview

    Why this matters

    Many businesses talk to customers on WhatsApp: questions, bookings and updates. An AI agent can answer the routine messages, but only if it replies without making people wait, remembers who it is talking to and lets a human know when a person is needed. Without that, the chat turns into a slow, forgetful inbox.

    A good result is a backend that receives each message, keeps a record of every user and conversation, and writes the AI reply in the background. Customers get automatic messages, staff get alerts, and the web layer stays free to take the next message. This project is that kind of backend, built for a client.

    The story

    Problem and approach

    The problem

    A business that talks to customers on WhatsApp must receive every message, match it to the right customer and answer without making anyone wait. An AI model takes longer to reply than a web request should wait. If the reply is written inside that request, slow answers hold up the service. Without saved history, the agent forgets the customer, repeats questions and wastes staff time.

    What I built

    I built a backend (a message receiver, a job queue, background workers and a database) in Python with FastAPI. The receiver takes each WhatsApp message through a webhook, which is a web address that the messaging service calls, and tracks the user. The AI work goes onto a Redis and Celery job queue, and a worker writes the reply, so the AI never blocks the web request. PostgreSQL keeps user state and the full conversation history. The Meta WhatsApp Business API and Twilio carry customer messages and operator alerts.

    What made it hard

    1. 01

      AI replies are slow

      A language model takes longer to answer than a web request should wait, so the reply cannot be written inside the request that receives the message.

    2. 02

      Remembering each customer

      Every message arrives on its own. The platform must match it to the right user and bring back their state and history, so the conversation continues across sessions.

    3. 03

      Reliable background work

      Moving the AI work out of the request needs a queue and workers. Jobs must be handled reliably, so a reply can be written after the request has ended.

    4. 04

      Two messaging providers

      Customer messages and operator alerts rely on the Meta WhatsApp Business API and Twilio, so the platform has to work with both side by side.

    1. 01

    3. 03

    Decisions

    Design decisions and trade-offs

    • Reply in the background, not in the request

      ChoiceI used Redis and Celery so the AI reply is written by a background worker, and the web request that receives the message does not wait for it.

      WhyAI models are slow compared with a web request. Keeping the AI off the request thread means a slow reply never blocks the receiver. I chose Redis and Celery for reliable background processing.

    • Keep state and history in PostgreSQL

      ChoiceI stored each user's state, the conversation context and the full history in a PostgreSQL database.

      WhyA database lets the AI agent carry on a conversation across sessions and keeps interactions personal. Data held only in memory would be lost whenever the program restarted.

    • Use both Meta and Twilio

      ChoiceI connected the Meta WhatsApp Business API and Twilio, for automatic customer messages and for alerts to human operators.

      WhyThe aim was multi-channel messaging: customers get automatic replies and notifications, and operators can be alerted.

    FAQ

    Questions about this project

    How does the platform reply on WhatsApp without making customers wait?

    The receiver tracks the user and hands the AI work to a background queue (Redis and Celery). A worker writes the reply, and it goes back to the customer when it is ready. The web request that received the message is not held up by the AI, so a slow answer never blocks the next customer's message.

    What is a webhook in a WhatsApp automation?

    A webhook is a web address on your server that the messaging platform calls each time something happens, such as a customer sending a message. The platform pushes the message to you instead of you asking for it. Here a FastAPI endpoint received each message this way, then tracked the user and queued the AI work.

    How does the platform remember each customer's conversation?

    It stores each user's state and the full conversation history in PostgreSQL. When a new message arrives, the platform matches it to the right user and brings back their context, so the AI agent can carry on across sessions instead of starting again. The database, not the program's memory, holds the record.

    Do human operators get alerts from the platform?

    Yes. The platform connected the Meta WhatsApp Business API and Twilio for automatic customer messages and for alerts to human operators. Which situations should alert a person is a business rule. For a new project I would agree that list with you first, before building anything.

    Can I see the code for this WhatsApp project?

    No. It was a client project built during an internship, and the repository is private, so I cannot share the code, screenshots or the client's name. I can explain the design on a call, and I can build something similar for you from scratch, using your own accounts and data.

    What should I prepare before building a WhatsApp AI agent?

    Prepare the questions customers ask most, the cases that need a person, and who should receive alerts. You also need a WhatsApp Business account. Account approval and message templates are set on Meta's side, so ask early, because they shape what the bot may send and how soon it can start.
