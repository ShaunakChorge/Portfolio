    AI scam honeypot that keeps scammers talking

    An Artificial Intelligence (AI) victim that keeps scammers talking and takes notes.

    This AI scam honeypot is a counter-scam system co-built with Prasanna Patil. An AI plays an easily fooled victim, keeps scammers talking and records the UPI payment IDs, links and phone numbers they reveal. A rule-based selector changes its style as scam risk grows, and a live dashboard shows what it collects.

    Overview

    Why this matters

    Banks, payment apps, telecom firms and messaging platforms face the same pattern. Scammers message many people at once, and each reply, click or payment costs a real person money and costs the business support time and trust. Blocking one number changes little, because the scammer moves to the next. What is usually missing is a record of how the scam works.

    A good result is a safe place where a scammer can be kept talking for as long as possible, while the business collects the payment IDs, links and phone numbers the scammer shares. That record can feed block lists and investigations. This case study covers a hackathon prototype of that idea, built with a co-builder, and says clearly who built which part.

    The story

    The problem: scammers waste real people's time

    The problem

    A blocked scammer just tries the next number, and nobody learns how the scam works. A bot that keeps scammers busy protects real people for as long as the chat lasts and leaves a record of exactly what the scammers ask for. Without that record, a fraud team may learn about a scam only after someone reports a loss.

    What I built

    The system is a FastAPI service with a React dashboard. It scores every incoming message for scam signals. Separately, a rule-based selector sets the bot's style: passive at first, vulnerable once a risk level (raised by shouting or very short messages) passes a limit, and stalling once enough details are collected. A persona prompt drives an AI model on Groq, which writes each reply from the last 10 messages. Pattern matching pulls out payment and contact details, and the live dashboard shows them. Prasanna Patil wrote the first version. I added the safety layer, moved the AI to Groq and rewrote the persona prompts and the link and phone patterns.

    What made it hard

    1. 01

      Staying believable

      A scammer may test whether a bot is on the other end. The persona must reply in short, casual messages, stay in character for many turns and never admit to being an AI.

    2. 02

      Hostile and abusive input

      The other side is a scammer, so messages may try to hijack the AI, for example with "ignore previous instructions", or flood the server. A cheap first line of defence must act before any message reaches the model.

    3. 03

      Messy payment details

      UPI IDs, links and phone numbers can be written in many forms, such as a link with no "http" or a number with spaces. A pattern wide enough to catch them will also catch some look-alikes.

    4. 04

      Two builders, one codebase

      The 18 build commits in the shared history fall on two days. Two people worked on one codebase, so I used separate branches that were merged back through pull requests.

    How it is built

    How the AI plays the victim

    1. 01Message inscammer text and conversation ID
    2. 02Safety checksinjection filter and request limit
    3. 03Score and stylesignals, risk, one of four styles
    4. 04Persona replyGroq model, last 10 messages
    5. 05Details savedUPI IDs, links, phone numbers
    6. 06Dashboardlive view of chat and details
    1. 01

      Intake, from Prasanna's first version. A FastAPI endpoint takes a conversation ID and a message, as text or a small JSON object, and needs an access key in a request header. Interactive API documentation (Scalar) is served alongside it.

    2. 02

      Safety layer, added by me. A filter checks for five known injection phrases and, on a match, sends a canned confused reply and does not store the message. A limiter gives each visitor address 1 request per second, with bursts of 5, and refuses the rest with HTTP 429.

    3. 03

      Scam scoring, from Prasanna's first version. 21 keyword patterns, such as lottery, tax, UPI and arrest, each add 0.2 to a message's score. At 0.7 or more the conversation is flagged, and the flag stays. The bot replies either way.

    4. 04

      Style selection, from Prasanna's first version. A rule-based selector picks one of four styles: passive on the first message, engaged after that, vulnerable once a running risk level passes 0.6, and stalling once more than three details are collected. Shouting or very short messages raise the risk level.

    5. 05

      Persona, memory and model, shared. Each conversation is kept in server memory under its ID. A persona prompt that I rewrote, plus the current style, goes to a model hosted on Groq with the last 10 messages. I moved this step from Gemini to Groq.

    6. 06

      Detail extraction, first version by Prasanna, link and phone patterns widened by me. Patterns pick UPI IDs, links and phone numbers out of each incoming message. Each record keeps its type, value, a fixed confidence (0.9, 0.95 and 0.8) and the turn it appeared in.

    7. 07

      Dashboard and delivery. Prasanna built the React dashboard, the Docker setup and the README. The dashboard shows the chat, the status, the current style, the collected details and the matched signals. I made small changes to it.

    Decisions

    Design decisions and trade-offs

    • Answer injection attempts with a canned reply

      ChoiceWhen a message contains an injection phrase, the bot sends one of four canned confused replies and skips the AI model, instead of returning an error.

      WhyThe injected text never reaches the model, and the other side still gets an ordinary reply, not an error. A keyword list is only a first line of defence, as the limits section says.

    • A token bucket for the request limit

      ChoiceI used a token bucket (an allowance that refills over time) for each visitor address: 1 request per second, with bursts of 5.

      WhyA quick burst of messages passes, but a sustained flood does not. The limiter is small, needs no extra service, and refused requests get the standard HTTP 429 answer.

    • A short, casual, slightly lazy persona

      ChoiceI rewrote the persona prompt so the bot plays a human, replies in one or two casual sentences, never admits to being an AI and is not too eager.

      WhyThe active persona is a student short of cash and keen on quick money; an elderly persona is defined but not used. The prompt aims for a believable young person, sceptical by default, which suits keeping a scammer talking.

    • Wider patterns for links and numbers

      ChoiceI widened the link pattern to catch web addresses without "http", and added capture of 10-digit and country-code phone numbers.

      WhyA strict pattern misses bare addresses and plain numbers. The cost is false matches, such as an email's domain read as a link or any ten-digit number read as a phone number, so the details are leads for a person to check, not verified facts.

    Results

    What it records for investigators

    Every number comes with how it was measured. The limits are part of the result.

    Results

    • The bot's style changes automatically: passive on the first message, engaged from the second, vulnerable once the risk level passes 0.6, and stalling once more than three details are collected.
    • UPI IDs, links and phone numbers are stored as structured threat records: type, value, a fixed confidence (0.9, 0.95 and 0.8) and the turn found. These confidence values are set in the code, not measured accuracy.
    • Each visitor address is limited to 1 request per second, with bursts of 5. A request over the limit gets HTTP 429.
    • The persona sees the last 10 messages for each reply, while the server keeps the whole conversation in memory under its ID.
    • A live dashboard shows warning signals, the current style and the details collected, next to the chat window where the tester plays the scammer.
    • Contribution record: of 19 changes in the shared history, I wrote 4 and merged 4 pull requests. The other 11 are Prasanna's, counted from the commit log.

    Limits to keep in mind

    • Detection is keyword based, not semantic. A message needs at least four of the 21 patterns to be flagged, so honest messages can be flagged and new tricks missed. It has not been measured on labelled conversations.
    • The injection filter is a keyword list, so it is a first line of defence, not a full defence. The limiter and the conversation memory live in server memory, so they reset on restart and do not work across several servers.
    • Patterns can misread: an email address can be recorded as a UPI ID, and a repeated detail is stored again each time. The collected details are not sent anywhere, so there is no report to a bank or an authority.
    • This is a hackathon prototype. The repository has no automated test suite, the sample access key and server address are written into the demo code, and if the AI provider fails the reply is an error message.

    In a business

    Where this kind of solution fits

    Situations where a team could use the same approach. These are examples, not past clients.

    • A bank or payments fraud team

      It wants a safe decoy that scammers can be steered to, so it can collect the payment IDs, links and numbers they use as leads for block lists and investigations.

    • A messaging or telecom trust team

      It wants to study how scam scripts unfold, what scammers ask for and how long they stay engaged, without putting a real customer in the conversation.

    • A university or security research lab

      It needs a controlled decoy to study scammer behaviour, with each message, the bot's style and the collected details visible on one dashboard.

    • A consumer awareness team

      It wants real examples of how current scams escalate, to train staff and warn customers. That would need conversations saved to a database, which this prototype does not do.

    FAQ

    Questions about the honeypot

    What is an AI honeypot?

    An AI honeypot is a decoy that looks like an easy target, so attackers waste their time on it and reveal how they work. Here an AI persona plays a victim in a chat and keeps a scammer talking. It records the payment IDs, links and phone numbers the scammer shares, ready for study.

    How do you create an AI agent?

    Give the AI a clear job, a way to read the situation and rules for what it may do. In this project each message is scored for scam signals. A rule-based selector picks one of four styles, and an AI persona on Groq writes the reply. Pattern matching then saves the details it collects.

    Who built which part?

    It was co-built with Prasanna Patil. Prasanna wrote the first version, the Docker setup and the README. I added the injection filter and the request limiter, moved the AI from Gemini to Groq, and rewrote the persona prompts and the link and phone patterns. Of the 19 changes in the shared history, I wrote 4 and merged 4.

    How well does it resist prompt injection?

    It has a keyword filter for five phrases, such as "ignore previous instructions", and a request limiter. On a match, the bot sends a canned reply and the text never reaches the model. That is a first line of defence, not a complete solution, because a determined attacker can reword a trick. A client project would add attack tests.

    What details does the honeypot record from a scammer?

    It records UPI IDs, links and phone numbers found in the scammer's messages. Each record keeps its type, the value, a fixed confidence level and the turn where it appeared. It does not look for bank account numbers or card numbers. Records stay in server memory until the server restarts, and the dashboard shows them as they arrive.

    How does the bot remember a conversation?

    Each conversation is stored in server memory under its ID, with every message, the scam score, the current style and the details found. For each reply the AI model sees the last 10 messages. Because the store is in memory, a restart clears everything. A client version would use a database.

    Does the honeypot report scammers anywhere?

    No. Apart from the request to the AI model, it makes no outgoing calls. The collected details stay in the reply it returns, in server memory and on the dashboard. Sending them to a fraud team, a block list or a case system would be an addition I can build for a client.
