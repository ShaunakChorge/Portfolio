      Read the case study: Observable AI Backend

      An LLM-routed API you can debug from the outside.

      A FastAPI service where an LLM picks one of three business actions (query tickets, create a ticket, sales report) and then summarises the result. A trace ID follows each /ask request through structured JSON logs, Prometheus metrics and OpenTelemetry traces in Jaeger, so a slow or failing call can be diagnosed from the outside. It runs fully offline with a deterministic keyword router when no API key is set. Built as a take-home for an AI platform role, with design decisions and rejected options logged in the repo.

      Problem

      An AI endpoint can return HTTP 200 and still be slow, degraded or quietly falling back to another model, and you only find out when users complain.

      Approach

      Stamp one trace ID on every log line and span of a request. Hand-write low-cardinality Prometheus metrics for requests, LLM latency, tokens and model fallbacks. Chain three Groq-hosted models with a per-model timeout and an explicit ‘degraded’ flag so a silent fallback is visible.

      Highlights

      • Trace ID on every /ask response and on every log line inside a request
      • Tracing demonstrated on a deliberately injected slow lookup (a toggleable O(n × m) join over 60,000 synthetic tickets): the tool span falls from about 15 s to under 50 ms once it is indexed
      • Three-model fallback chain with per-model timeout, a ‘degraded’ flag and a fallback counter
      • Runs with no API key or network: deterministic routing and 10 offline pytest tests
      • Docker Compose stack running the app, Jaeger and Prometheus together

      Key numbers

      Read the case study: Healthcare Policy RAG Assistant

      Cited answers, or an honest ‘not found’.

      A retrieval-augmented Q&A backend over six synthetic healthcare policy documents (appointments, discharge, HIPAA, insurance, refills, telehealth). A three-way router sends booking requests to a mock scheduling tool, chit-chat to a persona prompt and everything else to the RAG pipeline, which returns the answer with its source chunk and a confidence label. Weak retrievals are dropped before the LLM is called, so out-of-scope questions get a fixed fallback sentence instead of a guess. It was a prototype for an AI engineer assignment and uses no real patient data.

      Problem

      Healthcare answers must be grounded in the right document, and a confident wrong answer is worse than no answer.

      Approach

      Three anti-hallucination layers: intent gating, a similarity-score threshold applied before any LLM call, and a strict prompt with an exact fallback phrase. Prompts and tunables live in config files, and a chain of Groq models keeps the service running when one model is retired.

      Highlights

      • RAG answers return the source document, chunk and a confidence percentage
      • Score threshold filters weak chunks before the LLM ever sees them
      • Agentic 3-way router: mock scheduling tool, RAG, or persona chat
      • LLM fallback chain survives a model being retired with no code change
      • Dockerised FastAPI backend, Streamlit chat front end and pytest smoke tests

      Agentic Honey-Pot

      Read the case study: Agentic Honey-Pot

      An AI victim that keeps scammers talking and takes notes.

      Built with Prasanna Patil at a GUVI AI hackathon in February 2026, this counter-scam system turns the tables: instead of blocking a scammer, an LLM-driven persona plays a believable victim and keeps them talking. A FastAPI backend scores every incoming message against regex scam signals, shifts between four engagement styles - passive, engaged, vulnerable, stalling - and answers through a Groq-served persona that sees the last ten turns of the conversation. Regex extractors pull UPI IDs, URLs and phone numbers out of the chat as threat intelligence, and a React dashboard shows the detection signals, current style and extracted details live. My side was the hardening and LLM layer: a keyword-based prompt-injection filter, a per-IP rate limiter, the move from Gemini to Groq and the persona prompts.

      Problem

      A blocked scammer simply tries the next number, and nobody learns how the scam is run. Keeping them talking to a bot protects real people for as long as it lasts and leaves a transcript of exactly what they ask for.

      Approach

      Score each incoming message against regex scam signals and a threshold, then let a rule-based selector escalate the engagement style - passive early on, vulnerable when scam risk climbs, stalling once enough intel is banked - and reply as an LLM persona served by Groq. Extract payment and contact details with per-pattern regex confidence and stream everything to a React dashboard.

      Highlights

      • Rule-based strategy selector that escalates through passive, engaged, vulnerable and stalling styles as scam risk and collected intel grow
      • Keyword-based prompt-injection filter and a per-IP token-bucket rate limiter (1 request/s, burst of 5) - my hardening additions
      • LLM layer moved from Gemini to a Groq-hosted gpt-oss-120b, with rewritten persona prompts and the last ten turns as context
      • Regex extraction of UPI IDs, URLs and phone numbers, each with a fixed confidence per pattern type
      • Live React 19 dashboard, interactive API docs (Scalar) and a Dockerised setup

      Key numbers

      Last 10 turns per reply

      Read the case study: Speech Emotion Recognition

      Hear the mood in a voice clip, live from the mic.

      A deep-learning system that labels the emotion in a speech clip as angry, disgust, fear, happy, neutral, sad or surprise. Audio from four public corpora (RAVDESS, CREMA-D, TESS, SAVEE) was expanded with noise and pitch-shift augmentation into 48,648 feature vectors of zero-crossing rate, RMS energy and MFCCs, then fed to a 1-D CNN that reaches 93.87% on a random 20% held-out split (augmented copies of one clip can fall on both sides, so it is not speaker-independent). A notebook runs live microphone inference, and a Streamlit dashboard adds upload or record, class probabilities and waveform and spectrogram views.

      Problem

      Emotion lives in tone, pitch and energy rather than words, so a text model is the wrong tool.

      Approach

      Merge four corpora, augment each clip, extract hand-crafted audio features with librosa, train a five-block Conv1D network with batch-norm and dropout, then serve it through inference notebooks and a Streamlit dashboard.

      Highlights

      • Four public corpora merged into one 12,162-clip dataset
      • 4x augmentation (noise, pitch shift, both) giving 48,648 feature vectors
      • 93.87% accuracy and weighted F1 0.94 on a random 20% held-out split; per-class F1 between 0.92 and 0.97
      • Live microphone detection in a notebook and in a Streamlit dashboard

      Read the case study: Box Selection API

      The fewest, cheapest boxes for any order.

      A Django + DRF backend that takes a basket of products and recommends which shipping boxes to use. The packing logic is plain Python with no Django imports, so it is tested in isolation; it checks all six axis-aligned rotations and both volume and weight budgets, and returns a clear 400 naming the product when nothing fits. The repo’s AI_USAGE.md records the tools used (Claude for planning, Antigravity for implementation), the mistakes caught and how the result was verified.

      Problem

      Picking shipping boxes by hand over- or under-packs orders. The logic has to be correct, explainable and testable.

      Approach

      Three layers: inventory models, a pure-Python packing algorithm and a DRF API. A greedy heuristic sorts units by volume and puts each in the cheapest open box with budget left, otherwise opens the cheapest box that fits. It is deliberately not full 3D bin-packing, and the repo says so.

      Highlights

      • 27 tests: 11 algorithm unit tests and 16 API integration tests
      • Algorithm decoupled from the framework, with zero Django imports
      • Explicit error contract: a 400 naming the unshippable product, not an exception
      • Seed data chosen to hit edge cases, such as a tablet just over the small-box limit
      • AI_USAGE.md documents the tooling, accepted and rejected output and the checks run

      Read the case study: Core-Banking Text-to-SQL Assistant

      Plain English to executable Oracle SQL, fully on-prem.

      A continuous-control-monitoring assistant built at Claptek: a bank user types a reporting scenario in plain English and gets executable, multi-table Oracle SQL over a 1,628-table core-banking schema, generated fully on-premise. My slice was measurement and correction: an execution-accuracy harness that runs generated SQL against a real database and compares rows (replacing proxy metrics that had overstated quality), and an execution-guided self-correction loop that feeds real query failures back to the model.

      Problem

      Proxy metrics said the SQL generator was about 93% good; executing its queries showed the honest number was near zero.

      Approach

      Build the measurement first (rows-versus-gold execution harness, deterministic generation), then an execution-guided retry loop bounded at two passes - no bigger model, no fine-tuning, both disallowed by the client.

      Highlights

      • Execution-accuracy harness replaced flattering proxy metrics with honest, reproducible numbers
      • Self-correction loop raised account recall 34% to 54% and precision 19% to 27% with no model change
      • Value-glossary prompt injection so the model filters on enum codes that actually exist
      • Runs fully on-prem; no data, prompt or telemetry leaves the machine

    FAQ

    Quick answers about freelance projects, remote work and how an engagement starts.

    01 Do you take freelance projects?

    Yes – I take select freelance AI and backend projects alongside my full-time role as an AI Developer at Claptek. I keep the number small so each engagement gets real attention, and I’m upfront about scope and timelines before committing.

    02 What can you build for me?

    LLM applications and RAG pipelines that cite their sources, computer vision systems, FastAPI and Django backends, and automation such as scrapers and Telegram or WhatsApp integrations. It’s the same stack I use at work: Python, FastAPI, PostgreSQL and Docker, with LangChain, ChromaDB and local or hosted LLMs.

    03 How do we start a project?

    Send a short brief through the contact form or to shaunak.chorge@gmail.com: what you’re building, roughly when you need it and any constraints. I reply with honest feasibility notes and a proposed scope – no code gets written before we agree on both.

    04 Do you work remotely?

    Yes. I’m based between Pune and Mumbai, India, working in IST (UTC+5:30), and I’m set up for remote collaboration: my AI & ML internship at Shivohini Tech-AI was fully remote, and Git-based reviews and async updates are how I already work.

    05 What is your core tech stack?

    Python first: FastAPI, PostgreSQL, Docker, pandas and Streamlit are my daily drivers, alongside LLM APIs such as Groq and OpenAI. Project work adds LangChain, ChromaDB, TensorFlow, PyTorch, OpenCV, scikit-learn and React – the full tiered list is in the stack section.

    06 Can you take over or extend an existing codebase?

    Yes – most of my professional work has been inside existing systems: I integrated an LLM drafting service into a live Spring Boot and React audit product at Claptek and refactored core matching engines at Osource Global. I read before I rewrite, keep changes tested and leave the decision log in the repo.

    07 Have you shipped production AI systems?

    Yes – seven enterprise AI systems so far. At Claptek: an audit-finding drafting engine with code-enforced zero-hallucination gates (adopted into the client’s product the day after handover), a regulatory obligation-extraction service that pins 97.2% of records to exact source evidence, and the measurement layer of a core-banking text-to-SQL assistant. Earlier, at Osource Global, I worked on reconciliation, document and data tooling.
